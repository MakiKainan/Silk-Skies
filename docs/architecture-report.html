The five-minute tour

Read this section and you can hold a conversation about the code. Everything after it is a deeper look at one room of the building.

What exists right now

SILK SKIES is a 3D top-down duel game: you sail a spaceship around a circular arena, fire weapons at an enemy ship, and refit your gear between fights. Three milestones are done. M1 gave us sailing and the data system. M2 added combat. M2.5 added the inventory and refit screen. M3 added enemy AI, a boss, and a three-duel gauntlet. M4, the reward-and-loop milestone, is next.

Everything on screen is still placeholder boxes. That is on purpose: the code underneath is real, tested, and built so that real art can be swapped in later without touching the rules.

The building, in one picture

Think of the project as a building with six floors. The ground floor holds recipes (data). Each floor above uses the floors below it and never reaches back down to change them. On the side, three always-on services (autoloads) are reachable from every floor.

Seven ideas that explain most of the code

#IdeaWhat it means in practice
1Recipes vs. dishesA .tres file (a recipe) is authored and never changes. A specific drop of an item is a separate instance (a dish) with its own rarity and rolled stats. See section 4.
2One Ship for everybodyThe player and every enemy are the same Ship scene. Only the controller attached to it differs. Enemies are not special code.
3Controllers only give ordersKeyboard, AI and debug bots all use the same five commands: throttle, turn, hard burn, aim, trigger. The ship decides how to obey.
4Rules live in pure functionsDamage, sailing, stats and loadout rules are plain classes with no scene nodes. That is why 387 tests run in 15 seconds.
5Each part has one jobStats compute numbers, Movement moves, Health tracks HP, a WeaponController runs one weapon. If you are hunting a bug, the job tells you the file.
6Announce, don't commandWhen something happens (a hit, a death) the code emits a signal. Screens and effects listen. Gameplay never reaches into the UI.
7Tests guard the wallsEvery rule has tests. A fight can even be simulated headlessly at 340x speed to measure balance.
Why this matters to you
Almost every feature you will ask for next is either a new data file (new hull, weapon, enemy) or a new rule in one place. The map in the next section tells you which, and where.

The cast: every object in the game

Here is who is on stage, what each one does, and who it talks to. Start with the picture of a single Ship, because almost everything hangs off it.

Anatomy of a Ship

A Ship is built like this: the scene file scenes/ship/ship.tscn provides the fixed parts (Model, Stats, Movement, Health, HitFlash, HealthBar). Ship.setup(hull) then fills in the rest from data: it loads the hull's model, builds the collision shape, creates one mount per hardpoint, and computes stats. A controller is added afterwards by whoever spawns the ship (the Duel adds PlayerInput to the player; EnemyFactory adds AIController to enemies).

Command API: the five orders
set_throttle(-1..1) · set_turn(-1..1) · request_hard_burn(direction) · aim_at(point) · set_trigger(mode, held). Nothing else is needed to fly and fight. Add a future fighter-launch or ability and it becomes a sixth order, in one place.

Data: the recipe book

All game content is written as small files that describe things, not code that does things. This is the single biggest reason adding content is cheap.

What a recipe looks like

A hull, weapon or enemy is a Godot Resource: a typed bundle of fields saved as a .tres text file. Open data/weapons/railgun.tres and you see roughly this (trimmed):

[resource]
script = ExtResource("1_weapon")      # which class describes this file (WeaponData)
id = &"railgun"                       # unique name every other file uses to refer to it
display_name = "Railgun"
size = 1                              # 0 = Small, 1 = Large turret needed
targeting = 1                         # 0 Auto, 1 Manual, 2 Lock-on
projectile = ExtResource("2_proj")    # points at data/projectiles/railgun_slug.tres
cooldown = 2.5
charge_time = 1.0                     # hold the trigger this long before it fires
range = 70.0
roll_pool = ExtResource("3_pool")     # which stat lines a drop of this weapon can roll

The class (scripts/data/weapon_data.gd) declares which fields exist and their types; the Godot editor shows them as a form. You can edit a .tres by hand or in the editor's inspector. Nothing in the file does anything by itself.

The family tree of data

Recipe vs. dish: ItemData and ItemInstance

ItemInstance (scripts/systems/item_instance.gd) holds data_id, rarity and rolls (a list of StatMod). It looks the recipe up in ContentDB by id. If a recipe was deleted later, loading a save skips that item with a warning instead of crashing.

The three guards of the data layer

  • ContentDB (scripts/autoload/content_db.gd) scans res://data/ at startup, files every resource by its id, and exposes lookups: get_by_id, get_hull, hulls(), weapons(), items(), enemies().
  • ContentValidator (scripts/systems/content_validator.gd) checks everything the ContentDB loaded and prints problems in debug builds: duplicate ids, a hull whose hardpoint marker is missing from its model, a weapon with no projectile, an enemy carrying a Large weapon in a Small slot, phases out of order, an act with no encounters.
  • Tests load the real data/ folder and assert it is clean, so a typo in a .tres fails the test run, not your playtest.
The golden rule of data
Authored resources are never modified while the game runs. Tuning panels and rolled stats work on copies or on instances. If you ever see code writing into a HullData or WeaponData, that is a bug.

Stats: how numbers get combined

A ship's shield, speed or a weapon's damage is never typed in one place. It is built from layers. Understanding this one pipeline explains the hull files, the item rolls, the crew bonuses and the refit screen's green and red numbers.

The pipeline

A modifier, and its two dials

Every bonus anywhere in the game is a StatMod: which stat, how it applies (op) and to what (scope), with a value.

DialChoicesMeaning
opFLATadds a fixed amount: +50 shield
PERCENTscales: +0.25 means +25%. Percent bonuses add together (two +25% make +50%, not +56%)
scopeTHIS_ITEMonly the item carrying it (a weapon's own rolled +20% damage)
ALL_TURRETSevery weapon on the ship (the Gunner's fire-rate bonus)
SHIPthe ship's own stats (shield, armor, speed); also applies to every weapon's stats
A real bug this design taught us
A percent bonus on a stat that starts at zero stays zero, because zero times anything is zero. The Engineer's "techmod potency" starts at 0, so it had to be a flat +0.25 that the UI displays as "+25%". Rule of thumb: percent only for stats that already have a base value.

Two sets of stats: the ship and each weapon

Fire rate is stored as shots per second (cooldown is its inverse), so "+15% fire rate" is a plain percent bonus. A weapon with a longer range also gets proportionally longer-lived shots, so the extra range is real.

LoadoutStats.global_mods() is where gear is turned into the modifier list. It also keeps one weapon's rolled bonus from leaking onto another weapon, and applies the Engineer's potency to techmod items only.

Sailing: how a ship moves

Tuning workflow
In the sandbox press F1 for live sliders on the player's hull. Fly around until it feels right, press Print values (copied to the clipboard), paste them into the hull's .tres. The slider changes never touch the saved file.

Steering convention to remember when reading the code: the ship's nose points toward -Z; turning left increases the yaw angle; a turn input of +1 means starboard (right).

Combat: from trigger to damage

Three ideas: weapons decide when to fire, projectiles decide what they hit, and the damage model decides what that does.

Damage: shields, then armor, then hull

Damage typevs shieldvs armorvs hullUsed by
Energyx1.5normalx0.75Pulse Laser
Kineticx0.75ignores 50% of armorx1Autocannon, Railgun
Explosivex0.5normalx1.5Missile Pod

The design intent: energy strips shields quickly but struggles against armored hulls, kinetic punches through armor, explosive finishes hulls. Armor is flat, so many small hits suffer and few big hits don't. That is why the Pulse Laser is weak against the armored Warden. The table lives at the top of damage_model.gd and is the lever for global balance.

Weapons: three ways to fire

Arcs. Each hardpoint has an arc (360° all-round, 120° forward, 90° broadside). The maths is in scripts/systems/arc.gd. Turn on Show firing arcs in the F2 panel to see them as coloured wedges.

Lead. Auto weapons use first-order prediction: they aim at where a straight-moving target will be. You can dodge by changing velocity or Hard Burning. Manual weapons shoot exactly at the cursor; lock-on missiles home.

Projectiles: the life of a shot

Projectiles are spawned into a node in the group projectile_root (the scene provides it), never as children of the firing ship, so destroying a ship doesn't delete its bullets in flight.

Inventory and refit

Customization is built from three layers: the rules (ShipLoadout), the ship's reaction (Ship._apply_loadout) and the screen (InventoryScreen). The screen never changes the ship directly; it only asks the rules.

ShipLoadout: the rulebook of what goes where

ShipLoadout (scripts/systems/ship_loadout.gd) is a plain object, not a node. It holds two lists: slots (one per hull hardpoint, in the same order) and cargo (a fixed number of cells, empty ones are null so every item keeps its position). Everything the UI needs is a question or a command on this one object:

MethodAnswers / does
can_accept(kind, index, item)would this item be legal in that cell? Turrets need a hardpoint of the right type and size (a Small weapon fits a Large turret, not the reverse)
can_move(from, to)can the item in one cell go to another? If the target is occupied it is a swap, so both items must fit their new homes
move(from, to)does it, then emits changed. Returns false and changes nothing if illegal
add_to_cargo(item), equip_auto(item)first free cargo cell; first compatible empty hardpoint
take(kind, index)remove and return an item (the discard bin uses it)
rebind_hull(new_hull)switch hulls: items that fit re-mount, the rest go to cargo, anything with no room is lost
to_dict() / from_dict()save format. Unknown item ids are skipped; mounted items that no longer fit move to cargo

What happens when you drag an item

What Ship._apply_loadout does

  1. For every hardpoint: if a weapon item is in it and no matching WeaponController exists, make one (a new mount visual + controller). If the slot holds a non-weapon or is empty, remove the controller.
  2. Recompute the ship's stats from every equipped item (LoadoutStats.global_mods). Health reacts to the new maximums.
  3. Recompute each weapon's own stats (own rolls + ship-wide bonuses).
  4. Emit loadout_changed so the HUD and refit screen redraw.

Because one function does this for every change (drag, auto-equip, sandbox spawn, boss phase adding a weapon), there is only one place to get it wrong, and the tests cover it.

An enemy is a recipe plus a brain. The recipe says what it is; the AIProfile says how it fights; the AIController does the fighting using the same orders as you.

Game flow: scenes, runs and duels

How you get from the sandbox into a fight and back, who remembers what in between, and how pausing works.

RunState: the run's memory

player_hull, loadout
what you fly and carry. Created on demand as a Starter Frigate with Pulse Laser + Railgun
act, duel_index
which enemies are in the run and which one you are on (current_enemy(), has_next(), advance())
seed_value, make_rng()
a fresh random generator derived from seed + duel number, so Retry fights the same enemy with the same rolls
last_result
the stats of the most recent duel

What it does not have yet: saving to disk, hull damage carrying between duels, scrap, rewards. Those are M4. The save format for items and loadouts already exists (to_dict); only the file writing is missing.

How a duel is assembled

  1. Duel._ready() asks RunState for the player's hull and loadout, and for the current enemy.
  2. It builds the player ship (setup(hull, [], loadout)) at one end of the arena, adds PlayerInput, and disarms it.
  3. EnemyFactory.spawn() builds the enemy at the other end; its AI is switched off and its weapons disarmed.
  4. It adds the HUD, refit screen (InventoryScreen), DuelUI, damage numbers, and subscribes to EventBus for damage tallies and boss banners.
  5. It shows the preview and pauses the game. FIGHT arms everyone, switches the AI on and unpauses.
  6. When either ship dies (died signal) the duel records a DuelResult, waits 1.2 s, shows the result card and pauses again.
How pausing works (the one slightly fiddly spot)
Overlays and the refit screen use process mode Always so they keep running while the game tree is paused. The refit screen unpauses the game when it closes, so the duel listens for its closed signal and re-pauses if an overlay is still showing. Tests set duel.pause_enabled = false so a paused tree doesn't freeze the test runner.

Three guided walks through the code

Reading a map is one thing; walking a route is another. Each walk follows one thing end to end and names the file and function at every step.

Walk 1: you click, and a number floats off an enemy

  1. player_input.gd _physics_process: reads the left button and tells the ship the manual trigger is held.
  2. weapon_controller.gd _step_manual: if the cursor is inside the arc and the weapon is ready, builds charge; at full charge calls _fire.
  3. _fire sets the cooldown (1 / fire rate), spawns the first projectile (more if it is a salvo), emits fired and EventBus.weapon_fired.
  4. projectile.gd _physics_process: moves, ray-casts, finds an enemy ship, calls health.apply_hit(Hit) (or explodes).
  5. health_component.gd apply_hit: asks DamageModel.resolve, stores the new shield and hull, emits damaged and EventBus.ship_hit; if hull is gone it emits destroyed.
  6. damage_numbers.gd hears ship_hit and spawns blue, grey and red labels from the DamageResult.

Walk 2: you drag a Shield Capacitor onto the techmod slot

  1. item_slot.gd _get_drag_data: begins the drag, returns where it came from. All slots call _notification and highlight if loadout.can_move(...).
  2. On drop, _drop_data calls loadout.move(CARGO, i, SLOT, 3).
  3. ship_loadout.gd checks the capacitor is a techmod and slot 3 is a techmod hardpoint, swaps the cells, emits changed.
  4. ship.gd _apply_loadout: asks LoadoutStats.global_mods for the +50 shield / +4 regen, sets them on StatsComponent (which emits stats_changed).
  5. health_component.gd _on_stats_changed: the maximum grew by 50, so the current shield grows by 50 too.
  6. ship.gd emits loadout_changed; inventory_screen.gd redraws at end of frame and stats_panel.gd shows Shield 150 (+50) in green.

Walk 3: you press Start gauntlet and the Raider appears

  1. sandbox_panel.gd button calls sandbox.start_gauntlet(), which calls RunState.start_act(slice_act) (new seed, duel 0) and changes scene to duel.tscn.
  2. duel.gd _ready: reads the enemy from RunState (enemy_raider.tres) and builds your ship from RunState's loadout.
  3. enemy_factory.gd spawn: instantiates ship.tscn, sets team enemy, setup(raider hull), rolls each ItemSpec with ItemRoller from RunState.make_rng() and equips it, then adds an AIController using ai_brawler.tres.
  4. hardpoint_mount.gd builds the barrel; weapon_controller.gd is created for the autocannon; health_bar.gd floats the bar overhead.
  5. duel_ui.gd shows the preview card from the same EnemyData (hull numbers, style text, weapons coloured by rarity). The tree is paused.
  6. You press FIGHT: Duel.begin_fight() arms both ships, enables the AI and unpauses.

After any change

  1. Import (Godot does this on opening the editor; from the command line it is the --import step).
  2. Run the test suite. The validator test will catch a bad .tres (wrong slot, missing marker, duplicate id) with a message that names the file.
  3. Open the sandbox and look: F2 → spawn it, fight it, open the refit screen.
  4. If it affects balance, run the probe and compare duel lengths.

How to run things

# the engine (the _console build prints to the terminal)
GODOT = "C:\Users\Kevin Sukias\Downloads\New folder\Godot_v4.7.1-stable_win64_console.exe"

# after adding or renaming any class_name script:
GODOT --headless --path . --import --quit

# all tests (the --fixed-fps flag makes physics ~340x faster; always use it)
GODOT --headless --fixed-fps 60 --path . -s addons/gut/gut_cmdln.gd

# the balance probe
GODOT --headless --fixed-fps 60 --path . -s addons/gut/gut_cmdln.gd -gtest=res://tests/probe/probe_balance.gd
Why the tests can fight whole duels in seconds
Normally a game runs in real time, so a 90-second fight takes 90 seconds. --fixed-fps 60 tells Godot to advance 1/60 s per step as fast as the computer can. A minute of combat takes a fraction of a second, which is what makes the balance probe and AI tests possible.

How a test is written

  • Unit tests extend GutTest and call pure functions: DamageModel.resolve(10, KINETIC, 100, 3, 100) then assert the numbers.
  • Combat tests extend tests/helpers/ship_test.gd, which provides make_ship(), weapon(), sim() (steps weapons and projectiles by hand) and cleans up shots after each test.
  • Anything a test spawns must be registered for cleanup (autofree) or it keeps fighting during the next test. This bit us once.
  • Names read as sentences: test_a_phase_triggers_only_once. A failure message is the specification that broke.

Conventions and gotchas

The unwritten rules of this codebase, written down. Most of these exist because something went wrong once.

House style

  • Static typing everywhere. Godot warns on untyped declarations (project setting). Variables, parameters and returns carry types.
  • One class per file, named for the file (sailing_model.gd defines SailingModel). Files are snake_case, classes are PascalCase.
  • Constants at the top, with a sentence of why. Tuning numbers that are not per-item (the damage table, sailing constants) are named constants, not buried in logic.
  • Stat names are constants in Stats, never raw strings. A typo then fails at load time instead of silently doing nothing.
  • Comments explain why, not what. Public classes start with a ## description.

Coordinates and units

  • The play space is the flat plane y = 0. Ships are locked to it; projectiles are flattened to it.
  • A ship's nose points toward -Z. Yaw increases when turning left. Arc bearings are measured from the nose, positive toward starboard.
  • Distances are metres, speeds metres per second, turn rates degrees per second (converted to radians inside the maths).
  • Percent values in data are fractions (0.15 = 15%).

Godot-specific traps we have already stepped in

TrapWhat happensThe rule
Freed objects in typed variablesA weapon kept a reference to a ship that was destroyed and freed, then erred every frame passing it to a functionCheck is_instance_valid() before using any stored reference to something that can disappear. (Do not rely on != null.)

Never do these

  • Never write into an authored .tres at runtime. Make an instance or a copy.
  • Never let gameplay code call into a screen. Emit a signal or EventBus event instead.
  • Never give a controller a private back door into a ship. If the AI needs something the player doesn't have, add it to the command API for both.
  • Never store a ship, projectile or lock target forever without a validity check.
  • Never bypass ShipLoadout to change what is mounted; the ship would not update.

Architect's health check

An honest assessment of the building as it stands: what is solid, what is a shortcut, and what to prepare before M4 adds the most code.

What is solid

  • Clean layering. Data, rules, ship parts, scenes and screens depend downward only. The rules layer has no scene dependencies, which is why it is exhaustively tested.
  • One door for control. Player, AI, debug bots and tests all use the same five commands. That is why enemies were cheap to add.
  • Content scales by files. Eleven items, seven hulls, four AI styles, three enemies and an act exist without a line of content-specific code.
  • Events decouple feedback. New effects, sounds and counters can listen without touching gameplay.
  • Tested balance, not just logic. Duel length is measurable; the probe turned "too lethal" from a feeling into numbers.
  • The unglamorous parts exist. Content validation, a seeded RNG path, save-ready dictionaries and unknown-id tolerance are in place before they were urgent.
